# Обучающая платформа для студентов-стоматологов

Реализация по [docs/SPEC.md](docs/SPEC.md). Текущий результат — **этап 3: каталог, предметы и уроки**.
Готовы вход/профиль, редактор и публикация контента, публичный каталог, уроки
с пропусками и тестами, сохранение прогресса и серверная проверка доступа.
Очередь повторения, ИИ-тьютор и оплата — следующие отдельные этапы.
Добавлены три типа заданий: один вариант, несколько вариантов и короткий текст; [инструкция для автора](docs/exercises.md), [проверки](docs/validation-exercises.md).
Правила разработки: [AGENTS.md](AGENTS.md); решения: [docs/decisions.md](docs/decisions.md).

Для просмотра на Mac: [пошаговая инструкция](docs/macos.md), запуск — `bash start-mac.command`.

## Быстрый старт

Нужны Node.js 24 LTS, Corepack и Docker с Compose. Используйте закреплённый
pnpm 10.34.9 (`corepack pnpm …`, если глобальный `pnpm` другой версии).

```sh
cp .env.example .env # только при первом запуске, не перезаписывайте существующий .env
corepack pnpm install --frozen-lockfile
corepack pnpm db:generate
# Все сервисы: postgres, MinIO, Mailpit, миграции, сайт и worker.
docker compose up --build -d
```

Первый запуск MinIO собирает официальный исходный релиз; потребуется несколько минут.
В облаке с сессионным CA используйте вместо последней команды:

```sh
docker compose -f docker-compose.yml -f docker-compose.cloud.yml up --build -d
```

Для редактирования с горячей перезагрузкой запускайте сайт и worker на хосте:

```sh
docker compose up -d postgres minio mailpit
corepack pnpm db:migrate
corepack pnpm db:seed
corepack pnpm dev
# В другом терминале:
corepack pnpm worker
# В третьем терминале: проверка выполнения задачи отдельным worker
corepack pnpm worker:smoke
```

При переключении с полного Compose сначала остановите `web` и `worker`,
чтобы освободить порт 3000 и исключить лишних потребителей очереди.
Сайт использует порт 3000, `/api/health` проверяет реальный запрос к БД.
Mailpit: HTTP 8025, SMTP 1025; MinIO: API 9000, консоль 9001; PostgreSQL: 5432.
Порты Compose доступны только на loopback. Учётные данные Compose — только для разработки.
`docker compose down` останавливает сервисы, сохраняя тома с данными.

## Проверки

```sh
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm test
corepack pnpm test:integration # PostgreSQL + Mailpit должны быть запущены
corepack pnpm build
PLAYWRIGHT_BROWSERS_PATH="$PWD/tmp/playwright" corepack pnpm exec playwright install chromium
corepack pnpm test:e2e
```

Unit-тесты не требуют БД, Docker, внешних API или сети.
Typecheck/build требуют сгенерированного Prisma Client; первоначальная генерация
загружает schema-engine с `binaries.prisma.sh` с проверкой контрольной суммы.
Интеграционные и E2E-тесты требуют миграций и seed. Playwright запускает
отдельный сервер на порту 3100, использует только синтетические Telegram-подписи
и блокирует обращения к реальному Telegram. Тестовые ключи не пишутся в `.env`.
Для уже установленного совместимого Chromium можно указать
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium`.

В `.env.example` включены `mock`, `log`, `local`. SMTP реализован через nodemailer;
реальные LLM, платёжный и S3-адаптеры пока явно выдают
`ProviderNotImplementedError`, а не незаметно подменяются моками.
Моки запрещены в `NODE_ENV=production`. `pnpm build` собирает артефакт без ключей,
но запуск production потребует реальных адаптеров на следующих этапах.

## Что проверить вручную

- Главную страницу на телефоне от 360 px: читаемость, кнопка перехода к описанию,
  фокус клавиатуры, отсутствие горизонтального скролла.
- На машине с разрешёнными сетевыми доменами: полный `docker compose up --build -d`,
  завершение сервиса `migrate` с кодом 0, `worker:smoke` и `/api/health` со статусом 200.
- Повторный `db:migrate` не создаёт миграции заново; `docker compose down` / `up`
  сохраняет данные. Не используйте `down -v` или `db:reset` с нужными данными.

CI описан в `.github/workflows/ci.yml`: lint, typecheck, unit, build и отдельная
задача с PostgreSQL/Mailpit для интеграционных и E2E-тестов. Удалённый CI пока
не запускался. Результаты: [этап 0](docs/validation.md), [этап 1](docs/validation-stage-1.md), [этап 2](docs/validation-stage-2.md), [этап 3](docs/validation-stage-3.md).

## Вход и профиль

1. Примените миграции и выполните `pnpm db:seed` (полный Compose делает оба шага
   в сервисе `migrate`; cloud setup/maintenance также выполняют seed).
2. Откройте `/login` по адресу из `APP_URL`. В режиме `MAIL_TRANSPORT=log` письмо
   сохраняется в игнорируемый `tmp/mails` процесса сайта: на хосте — в checkout,
   при Compose — в томе контейнера `web`. Откройте ссылку из поля `text` **в том
   же браузере**, где запросили письмо, и подтвердите вход.
3. Для Mailpit задайте `MAIL_TRANSPORT=smtp`. На хосте SMTP доступен по
   `localhost:1025`; Compose автоматически задаёт `SMTP_HOST=mailpit` для
   web/worker. Письмо появится в интерфейсе Mailpit на порту 8025.
4. При первом входе заполните имя и установите согласие. До этого кабинет
   недоступен. Юридические документы версии 0.1 — явно отмеченные заглушки.
5. В профиле можно менять данные, подтверждать новую почту, привязывать Telegram,
   выходить из текущей сессии или со всех устройств. Новый email не заменяет
   старый до подтверждения; конфликтующие аккаунты не объединяются.

Администраторы задаются списком `ADMIN_EMAILS` через запятую. Seed назначает им
роль, но не подтверждает адрес и не создаёт сессии: вход всё равно требует письма.
`EDITOR` и `ADMIN` допускаются в `/admin`; для `USER` возвращается HTTP 403.
Редактор контента доступен в `/admin`.

Для живого Telegram Login локально или на VPS нужны **свой** бот, настройки
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и домен, привязанный через BotFather
`/setdomain`. В облачных тестах реальные ключи не используются. Без настройки
бота работает вход по почте; виджет заменяется пояснением.

`APP_URL` определяет доверенный origin и ссылки в письмах; в production требуется
HTTPS. `sid` и `login_flow` — HttpOnly / SameSite=Lax, Secure на HTTPS.
За reverse proxy задавайте `TRUST_PROXY=true` **только** если он заменяет
`X-Real-IP` проверенным адресом клиента. Иначе применяется общий безопасный
IP-bucket `unknown`; присланным клиентом forwarding-заголовкам приложение не доверяет.
Внешний access-log также должен скрывать query-параметры `/auth/verify`.

Продуктовые параметры — в `AppSetting`, тарифы — в `Plan`. Кеш настроек — 60 секунд;
невалидные значения заменяются безопасными дефолтами. Повторный seed не перезаписывает
отредактированные цены, настройки и контент. Демо-темы остаются `DRAFT` и
`needsExpertReview=true`: по 10 пропусков и 5 вопросов, всего 3 диагностических.
Справочник вузов пуст до заполнения владельцем; свободный ввод доступен.

В этой облачной среде домашний pnpm cache доступен только для чтения, поэтому
`.npmrc` хранит store в игнорируемом `tmp/pnpm-store`. Для тестов с БД не используйте
боевую базу: проверки создают и удаляют только собственные синтетические записи.

## Редактор контента

- `/admin` — поиск и пагинация предметов; добавление предмета.
- `/admin/subjects/[id]` — настройки, разделы и темы предмета.
- `/admin/topics/[id]` — Markdown с подсветкой `[[…]]`, интерактивное безопасное
  превью, ошибки со строками, автосохранение, вопросы и публикация.

Роли `EDITOR` и `ADMIN` имеют доступ; проверка выполняется также в каждом API.
Публичные учебные маршруты пока не реализованы. Для авторского сценария
используйте чек-лист [проверки этапа 2](docs/validation-stage-2.md).

Для публикации: предмет должен быть опубликован; у темы должны быть пропуски,
5–15 валидных вопросов, автор, рецензент, источники и явная экспертная отметка.
Переведите тему в «На проверке», затем нажмите «Опубликовать». Изменение
опубликованного текста или вопросов возвращает тему в черновик. Повторная
публикация без изменений сохраняет версию и ID. Используемые записи защищены
от удаления, исчезнувшие пропуски и вопросы архивируются с сохранением истории.

Автосохранение обнаруживает конфликт двух редакторов; перед обновлением страницы
скопируйте свой локальный текст. Новая миграция добавляет editRevision без сброса
данных. Seed больше не восстанавливает старые fixture-гaps в отредактированной теме.

При публикации сохраняется транзакционная задача `content-index`. Обработчик
RAG/эмбеддингов будет добавлен на этапе 5; текущий worker его ещё не обрабатывает.
Входящие ID в обработчике должны проверяться по актуальным status/version.

Административные DTO содержат правильные ответы для редактора. Публичные
маршруты этапа 3 должны использовать отдельные DTO без ответов до ответа
пользователя; `/api/admin/content/*` остаётся закрытым по роли.

## Каталог и уроки

- Откройте `/subjects` на локальном сайте (порт 3000), выберите предмет и тему.
  Каталог показывает только опубликованный контент. Исходный медицинский seed
  остаётся DRAFT/needsExpertReview: после экспертной проверки публикуйте материал
  через редактор, как описано выше.
- Бесплатная тема доступна без входа. Заполните пропуски, запустите тест, обновите
  страницу: ответы и незаконченный тест восстановятся в том же браузере.
- «Пройти заново» у методички — тренировка без перезаписи первых ответов.
  Повторный тест — отдельная попытка, лучший результат сохраняется.
- Платная тема показывает безопасное превью и paywall; остальной текст отсутствует
  в HTML. Доступ открывает действующая Subscription или AccessGrant, проверяемая
  сервером. Checkout пока не реализован (этап 7), кнопки фиктивной покупки нет.
- Браузерные тесты создают и удаляют синтетические опубликованные темы, проверяют
  гостевое прохождение, перезагрузку, клавиатуру, изоляцию и закрытые API. Скриншоты:
  `tmp/screenshots/lesson-stage-3-chromium.png` и `lesson-stage-3-mobile.png`.
- Автосоздание карточек и `/review` выполняются на следующем этапе 4.

Временный тестовый просмотр с отдельной базой: [docs/preview.md](docs/preview.md).
