## 2026-11-06 — этап 1: данные и вход

1. Перенесена полная схема раздела 8, добавлены явные FK и обратные связи.
   Удаление — Restrict, исключение — Session → User (Cascade), как в ТЗ.
   Дополнительно: nonce/intentUserId в LoginToken для привязки подтверждения
   к браузеру и аккаунту, TelegramAuthUse для одноразовости подписанного payload,
   AuthAttempt для rolling rate limit. Добавлена отсутствовавшая уникальность
   demoSessionId/questionId у Card. Размерность vector — 1536; смена требует миграции.
2. Seed — транзакционный upsert без перезаписи пользовательских изменений.
   Тарифы, настройки, тексты и юридические заглушки хранятся в БД. Два учебных
   fixture-файла дают 20 пропусков, 10 вопросов и 3 диагностических вопроса.
   Темы остаются DRAFT / needsExpertReview=true. Извлечение seed-пропусков —
   локальная подготовка fixtures, не замена парсеру публикации этапа 2. GapKey —
   SHA1 предложения с нормализованными пробелами/регистром, разделителя `|` и ответа;
   ID сохраняются при повторном seed. BlockKey fixtures временные, до парсера этапа 2.
3. Для magic link выбрано подтверждение POST-кнопкой: GET не расходует токен
   и безопасен для почтовых сканеров. LoginToken содержит только SHA256 токена
   и nonce. Ссылка требует cookie браузера, запросившего письмо; перенос между
   браузерами/устройствами не поддерживается. Это явно объясняется в письме и UI.
   Устанавливаются HttpOnly/SameSite=Lax cookie, Secure на HTTPS. Origin проверяется
   для каждой мутации; production APP_URL обязан использовать HTTPS.
4. На странице подтверждения используется Referrer-Policy `origin`: `no-referrer`
   приводил в Chromium к Origin:null на POST и блокировал легитимное подтверждение.
   Теперь URL с токеном не передаётся в Referer, а защита Origin остаётся строгой.
   Next dev access-log исключает `/auth/verify`; внешний proxy-log также должен
   скрывать query. Локальные письма и store остаются вне Git.
5. Вход и привязка способов — разные намерения. Смена email требует действующей
   сессии того же аккаунта, nonce и подтверждения; остальные сессии отзываются.
   Аккаунты никогда не объединяются автоматически. Проверки токена, его расход,
   обновление пользователя и создание сессии выполняются в одной транзакции.
   Advisory locks защищают rate limits и лимит параллельных сессий от гонок.
6. Сессии проверяются по хешу, сроку и blockedAt/deletedAt при каждом обращении.
   Proxy обновляет DB expiry и cookie не чаще раза в сутки; серверные страницы и API
   дополнительно проверяют доступ. До актуальных версий согласия/оферты кабинет
   закрыт. USER получает 403 на `/admin`, EDITOR/ADMIN допускаются; остальные
   административные возможности относятся к следующим этапам.
7. Telegram: официальный Widget v22, HMAC-SHA256 с ключом SHA256(bot_token),
   constant-time сравнение, проверка времени и одноразовый hash в БД. Callback
   принимается от iframe самого виджета и только с oauth.telegram.org; затем
   отправляется на same-origin POST и повторно проверяется сервером. Стандартный
   data-onauth в текущем официальном скрипте использует eval; прямой message bridge
   позволяет не добавлять unsafe-eval в production CSP. Контракт проверен по
   официальному скрипту и offline iframe fixture. Реальный бот не подключался.
8. SMTP реализован через nodemailer (новая runtime-зависимость); TLS verification
   сохраняется, production требует TLS. yaml используется только для seed-файлов.
   Обе зависимости нужны требованиям этапа. Ошибка отправки аннулирует токен;
   адреса, ссылки и секреты в stdout не печатаются. Прочие реальные провайдеры
   остаются задачами последующих этапов.
9. `TRUST_PROXY=false` — дефолт. Только при явно доверенном reverse proxy берётся
   его X-Real-IP; иначе общий bucket unknown. Боевые секреты в cloud не запрашивались.
   Для проверки живого Telegram нужны собственный бот и /setdomain локально/VPS.
10. Домашний pnpm store в новом runtime read-only; добавлена переносимая `.npmrc`
    с store-dir=tmp/pnpm-store. Setup/maintenance и Compose после миграций вызывают
    идемпотентный seed. Playwright использует отдельный сервер 3100, синтетические
    подписи и блокирует реальные Telegram-запросы. В CI добавлен отдельный job
    с PostgreSQL + Mailpit. Сами удалённые workflow не запускались.
11. Механика переноса DemoSession/UTM — этап 6; удаление/обезличивание аккаунта —
    этап 8; очистка устаревших auth/rate-записей и production-эксплуатация —
    стабилизация. Полноценный кабинет, редактор и остальные P0 не подменяются
    макетами в рамках этапа 1.

## 6 ноября 2026 — этап 2: контент и админка

1. Добавлены unified/remark-parse/remark-gfm, react-markdown и rehype-sanitize:
   они нужны для полноценного Markdown/GFM и безопасного превью. @types/mdast
   используется для типизированного AST. Редактор построен на существующих
   React/shadcn-компонентах без отдельного UI-фреймворка.
2. Парсер — чистая серверная функция `parseTopic`. BlockKey = транслит ближайшего
   заголовка + номер блока; повторы заголовков получают суффикс. GapKey = SHA1
   NFKC/whitespace/lowercase-нормализованного контекста с `____`, `|` и ответа.
   Дистракторы не входят в идентичность. Несколько одинаковых пропусков с тем же
   контекстом и ответом считаются ошибкой: существующий unique key не позволяет
   однозначно сохранить отдельные записи. Фрагменты кода и экранированные скобки
   игнорируются. Изображения — P1 и пока блокируют публикацию.
3. Перед разбором AST разделители вариантов в пропусках маскируются символом той
   же UTF-16-длины: GFM не разбивает варианты на ячейки таблицы, offsets остаются
   исходными. Превью получает результат разбора от защищённого серверного API,
   а клиент заменяет только подтверждённые диапазоны на интерактивные элементы.
   Raw HTML пропускается; rehype-sanitize дополнительно фильтрует URL и элементы.
   ID-якоря генерируются приложением, не берутся из пользовательского HTML.
4. CRUD обслуживается через `/api/admin/content/*`. Каждый обработчик сам
   проверяет сессию, EDITOR/ADMIN, актуальное согласие и Origin для мутаций.
   Ответы вопросов доступны только в административном контексте. Все входы
   валидируются zod, тело ограничено 512 КБ, Markdown — 100 000 символов.
5. Subject/Section/Topic получили `editRevision`. Topic-изменения и работа с
   вопросами сериализуются advisory lock по теме; несовпадение версии даёт
   отдельный код stale/409. Автосохранение использует общий promise и refs,
   сохраняет последующие правки после завершения текущего запроса. При конфликте
   текст остаётся локально, повторная запись блокируется до явного обновления.
6. Модель ТЗ хранит один contentMd без опубликованных ревизий. Поэтому изменение
   опубликованного материала переводит тему в DRAFT, снимая прежнее одобрение.
   Редактор получает предупреждение об этом. Публикация разрешена из REVIEW
   после явной экспертной отметки, автора/рецензента/источников и 5–15 вопросов
   (границы — AppSetting). Предмет также должен быть опубликован. Повторный
   запрос для уже PUBLISHED темы — no-op: версия/ID/очередь остаются прежними.
7. Публикация транзакционно upsert-ит Gap по ключу, архивирует исчезнувшие и
   приостанавливает их Card. Повторное появление возвращает старый ID. Удаление
   вопроса — архивирование; попытки и карточки сохраняются. Физическое удаление
   темы/раздела/предмета разрешено только без защищённых зависимостей; FK-ошибка
   откатывает весь запрос. Пользовательские ответы и прогресс не удаляются.
8. Задача content-index записывается pg-boss через адаптер текущей Prisma
   transaction. Текст SQL генерирует pg-boss, значения передаются параметрами.
   Невозможность записать задачу откатывает всю публикацию. Обработчик индексации
   относится к этапу 5; он должен сверять опубликованность/версию и игнорировать
   удалённые или устаревшие темы. Пока ни LLM, ни внешние сервисы не вызываются.
9. После мутаций сбрасываются кеши каталога, предметов, уроков и admin-layout
   через revalidatePath; приватные API возвращают no-store. Ограничения числа
   вопросов, размер страницы и debounce автосохранения хранятся в AppSetting.
10. Seed переведён на общий парсер. После первого editor editRevision/публикации
    он не добавляет старые fixture-пропуски/вопросы в изменённую тему. Для ещё не
    редактированных демо обновлены прежние временные source/block keys с
    сохранением ID и остальных данных. Регрессия проверена в отдельной чистой БД.
11. В таблицах и превью не появляются вымышленные медицинские материалы:
    синтетические E2E/integration-объекты удаляются после тестов, исходные
    демо-темы остаются непроверенными черновиками. Публикация контента в тесте
    не является публикацией облачной среды или внешним деплоем.

12. Production-сборка в ограниченной песочнице сохранила ошибку Turbopack
    binding/EPERM. Прямая проверка разрешённого локального bind прошла, поэтому
    удалён только сгенерированный `.next/cache`. С новым кешем и доступом к
    локальному порту исходный `pnpm build` успешно завершился; зависимости,
    проверки и конфигурация production-сборки для этого не ослаблялись.

2. Страницы `/subjects`, `/subjects/[slug]`, `/learn/[subject]/[topic]` рендерятся

   не публикуются автоматически ради демонстрации интерфейса.
3. `lib/access.hasAccess` — общая проверка бесплатного урока, подписки на предмет /
   все предметы и временного ручного AccessGrant. ACTIVE действует строго до конца
   периода; PAST_DUE — до конца периода + billing.graceDays. Просроченный, будущий,
   чужой доступ, заблокированный/удалённый платный аккаунт отклоняются. Чтение урока
   и каждый API ответа заново проверяют доступ и опубликованность на сервере.
4. Публичные DTO отделены от редакторских. `contentMd`, gapKey, правильный индекс,
   explanation и correctOptionIds до ответа не сериализуются. Варианты пропуска
   сортируются по SHA-256(actor + gap ID + option text): порядок не зависит от
   исходной позиции ответа, стабилен после перезагрузки. Публичный markdown содержит
   только контролируемые ссылки-плейсхолдеры; raw HTML пропускается, URL санируются.
   После ответа обратная связь раскрывается только для отвеченного пропуска/вопроса.
5. Закрытый урок передаёт клиенту только первые lesson.paywallPreviewBlocks блоков;
   пропуски в них заменены на «____» без вариантов. Остальной текст, вопросы и ответы
   отсутствуют и в HTML, и в React Flight. Размытие рисуется из пустых декоративных
   полос, а не из скрытого медицинского текста. Источники платного урока также
   не сериализуются до получения доступа.
6. Бесплатный урок доступен гостю без регистрации. Proxy выдаёт непрозрачную
   HttpOnly/SameSite=Lax cookie; в БД сохраняется только её SHA-256 в anonId
   DemoSession. Сервер передаёт cookie в текущий SSR-запрос; поэтому первый рендер
   сразу использует стабильный порядок вариантов. lesson.guestDays ограничивает
   срок cookie и поиска гостевой сессии. ID сессии не принимается от клиента.
   Это минимальный анонимный контекст урока; воронка и перенос в аккаунт — этап 6.
7. Первый GapAnswer неизменяем. «Пройти заново» очищает только отображение;
   тренировочный ответ оценивается сервером без изменения статистики первого.
   Прогресс вошедшего — TopicProgress, гостя — агрегация его GapAnswer/TestRun.
   Прохождение требует всех действующих пропусков и лучшего теста не ниже
   lesson.passThreshold. Архивные пропуски не участвуют в счётчике.
8. Тест запускается явно; незаконченная попытка восстанавливается при перезагрузке.
   Повторное прохождение создаёт TestRun, лучший балл не уменьшается. Добавлены
   TestRun.topicVersion и unique(testRunId, questionId): версия защищает попытку
   от изменений вопросов после повторной публикации, unique и advisory lock —
   от двойного ответа. Старую попытку другой пользователь использовать не может.
9. Запись ответов, пересчёт балла и прогресса выполняются в одной транзакции
   под тем же content:topic lock, что и публикация/редактирование. Неизвестные
   варианты, чужой вопрос, устаревшая версия, неопубликованная тема отклоняются
   до записи. Все POST проверяют Origin и строгую zod-схему, ответы no-store.
10. Чтения и отправки урока используют consumeLimit и UsageCounter: общий
    атомарный лимит lesson.requestsPerMinute на актёра, минутное окно. Настройки
    лимита, гостевой cookie, порога прохождения и превью — AppSetting.
11. Новых зависимостей нет. Существующий ReactMarkdown/GFM/rehype-sanitize
    используется отдельным публичным компонентом; административный preview
    с правильными ответами никогда не подключается к уроку.
12. Неотвеченные пропуски имеют одинаковую минимальную ширину. Это уточнение
    требования «по ширине правильного ответа» сохраняет неизвестность правильного
    варианта: длина плашки не позволяет сопоставить ответ с длиной одного из чипов.

   не включены. Парольный вход отложен, как предложил пользователь. Форма
   входа поясняет, что ссылка служит первому и повторному входу в один аккаунт.
2. Редактор сохраняет прежние API, автосохранение, версии и права, но разделён
   навигацией на пять шагов. Метаданные рецензии и действия публикации собраны
   в конце; добавлены подсказки по адресу, оформлению, вопросам и эталонам.
   Технический список готовности не обозначает клиническую достоверность.
   Серверные проверки публикации остаются обязательными. Ошибка явного действия
   прокручивает к сообщению; состояние урока также видно у кнопок публикации.
3. Кнопка изображения принимает PNG/JPEG/WebP. Сервер проверяет исходную сигнатуру,
   размер, декодирование, число страниц и пикселей, корректирует ориентацию,
   уменьшает сторону и преобразует в WebP без исходных метаданных. SVG, HTML,
   анимация, внешние URL и image-reference разметка не принимаются.
   Явная зависимость sharp закреплена в уже использовавшейся Next версии 0.35.5.
4. TopicImage хранит принадлежность теме и размеры, файл — по непрозрачному ключу
   в существующем StorageDriver. Для local используется постоянный Docker-том.
   Лимиты размера/пикселей/стороны/числа файлов/запросов — AppSetting.
   Multipart ограничен при чтении потока независимо от Content-Length.
   Нормализация идёт после проверки роли, запись повторно проверяет роль и
   назначение под общим локом прав и локом темы; при отказе файл убирается.
5. GET картинки проверяет текущую тему, публикацию, экспертную отметку,
   наличие ссылки в текущем тексте и hasAccess. Сотрудник может просматривать
   черновик только в разрешённом предмете. Ответы private/no-store, без
   публичных presigned URL. Next Image используется unoptimized: оптимизатор
   не должен запрашивать защищённую картинку без cookies пользователя.
6. Публикация не допускает изображения другой темы или неизвестного ID.
   Файлы неизменяемы; смена ссылки проходит обычную повторную проверку версии.
   Подпись входит в текст для поиска тьютора, сами пиксели модель не анализирует.
   Удаление темы сначала фиксируется в БД, затем очищает файлы. Неиспользуемые
   загрузки учитываются в лимите; полноценная медиатека и S3 — не эта задача.
7. Проверка ответов ученика остаётся сравнением с эталонами без LLM. Отдельный
   шаблон рецензии включает методичку, сохранённые вопросы, эталоны пропусков
   и источники, без метаданных аккаунта. Известные форматы ПДн редактируются,
   приватные URL картинок заменяются подписями. Копирование не вызывает API,
   не утверждает медицинскую точность и не меняет отметку эксперта.
8. `/admin/integrations` доступен только ADMIN, показывает безопасные статусы
   и пошаговые пояснения, не значения ключей и не ложное «соединение работает».
   Ключи остаются в ENV. Нужны отдельно чат-модель и embeddings 1536; реальные
   провайдеры в облаке не вызывались. Для Telegram отдельно нужны бот и домен;
   наличие токена на localhost не считается успешным входом.
9. Опциональный Compose-файл явно включает настройки LLM/Telegram из `.env`
   в той же preview-базе. Он не включает боевые платежи, внешнюю почту или S3.
   Обычный запуск для Mac по-прежнему безопасно оставляет моки. Конфигурация
   проверена с фиктивными значениями, без платных запросов или публикации.
10. Новая миграция добавочная. Пошаговые инструкции объясняют поля, создание
    урока, виды проверки, промпты и подключение без предположения об IT-опыте.
    Сайт и облачная среда не публиковались, прежний медицинский контент не менялся.

### Этап 9: импорт материалов

- Пользователь просит быстрее завершить P0 MVP; парольный вход, новые визуальные

  удаления данных пациентов перед загрузкой.
- Исходники удаляются после терминального статуса; журнал хранит статусы и
  ссылки на черновики. При ошибке удаления worker повторяет очистку.
- Генерация всех частей валидируется до единой транзакции создания тем.
  Ошибка не оставляет половину уроков. runToken и аренда защищают от дублей
  после повторной доставки; истёкшие задания восстанавливаются. Роль и
  назначение проверяются до генерации и заново под блокировкой ролей при записи.
- В mock-режиме только технические упражнения по источнику, без утверждений
  о медицинском качестве. В production импорт использует общий LLMProvider,
  отдельный системный промпт и один повтор невалидного JSON. Публикация
  по-прежнему требует ручной экспертной проверки.

## 2026-11-11 — понятные причины отказа в публикации

- API уже возвращал пути ошибок Zod, но клиентский `requestContent` терял
  их и оставлял только общее сообщение. Теперь поля передаются до редактора
  с русским названием, объяснением и адресом нужного элемента. Сообщения
  числовых и строковых ограничений переведены на русский.
- Ошибки параметров показаны под полями и в общем списке со ссылками.
  Ошибка сохранённого вопроса содержит его номер и идентификатор: ссылка
  открывает нужный вопрос и фокусирует поле. Список готовности поясняет
  отсутствующие источники, количество вопросов и проблемы заданий.
- Проверки публикации остались на сервере: принадлежность изображений,
  разметка, пропуски, валидность вопросов, публикация предмета, экспертная
  проверка и статус REVIEW. Не добавлялись автоматические подтверждения
  медицинского содержания, миграции или зависимости.
- Проверки используют синтетические уроки и заглушки внешних сервисов.
  Публичный сайт и реальные интеграции не запускались.
