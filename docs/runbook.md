# Запуск, обновление и восстановление

## Что уже можно использовать

Локальный MVP запускается на Mac через `bash start-mac.command`. Сайт —
http://localhost:3000, тестовые письма — http://localhost:8025. Работают
кабинеты, редактор и изображения, импорт, задания, повторение, тестовый
тьютор и тестовая оплата. Этот режим не списывает деньги и не отправляет
запросы настоящему ИИ. Реальные подключения и публикация выполняются отдельно.

Не удаляйте Docker-тома и не запускайте `down -v`, `db:reset` или очистку данных
Docker Desktop: в томах находятся пользователи, уроки и результаты.
Обычная замена ZIP и повторный запуск сохраняют их.

## Резервная копия на Mac — пошагово

1. Убедитесь, что Docker Desktop работает и проект уже запускался.
2. Откройте Терминал в папке проекта, как при обычном запуске.
3. Выполните:

   ```bash
   bash backup-mac.command
   ```

4. Сайт ненадолго остановится, затем запустится снова. Закончите редактирование
   урока до запуска команды. Копия создаётся в `Документы/Emil2-Backups`;
   папка откроется автоматически. Каждая копия — отдельная папка `emil2-ДАТА-...`.
5. Скопируйте всю эту папку на другой защищённый диск. Внутри находятся база,
   изображения и контрольные суммы. Копия содержит данные аккаунтов: не
   отправляйте её в чат и не кладите в открытое облачное хранилище.

В локальном режиме старые копии автоматически не удаляются. Делайте копию
перед обновлением и после добавления важных уроков. Файл `.env` с настройками
и секретами в архив не включён; храните его отдельно в менеджере секретов.

## Проверка восстановления без замены текущего сайта

В той же папке проекта:

```bash
bash scripts/ops/restore.sh preview "/полный/путь/к/Emil2-Backups/emil2-ДАТА-СУФФИКС" emil2_restore_check1
```

Замените путь своей папкой резервной копии. Команда проверит контрольные суммы,
создаст **новую** базу `emil2_restore_check1` и отдельный том изображений.
Существующая база и текущий сайт не меняются. Если база или том уже существуют,
выберите новое имя, например `emil2_restore_check2`: перезаписи в скрипте нет.

Для фактического перехода на восстановленную копию нужен отдельный Compose-
файл: `DATABASE_URL` у web/worker/migrate должен указывать на новую базу,
а `uploads` у web/worker — на напечатанный скриптом новый том. Используйте
**только переопределение**, без удаления старых томов. Проверьте сайт и лишь
потом меняйте постоянную конфигурацию. Для новичка этот шаг лучше выполнить
вместе с разработчиком: здесь выбирается, какая история данных станет рабочей.

Восстановление не выполняет повторный seed и не меняет роли или тарифы.
После восстановления более старой базы дополнительно применяются новые
миграции. Оставшиеся на момент копирования незавершённые импорты/платежи
нужно проверить по их статусам и у платёжного провайдера.

## Рабочий сервер — подготовка, без публикации

Подготовлен самостоятельный `docker-compose.production.yml` и
`Dockerfile.production`. Они не применяются обычным запуском Mac.
Конфигурация рассчитана на VPS в РФ, ориентир — 4 vCPU / 8 ГБ RAM;
производительность проверяется ещё раз на выбранном сервере. Предусмотрены
три веб-контейнера, worker, PostgreSQL и Caddy. Наружу открываются только
80/443; база и сайт за прокси не имеют опубликованных портов.

Рабочие БД, файлы и резервные копии должны храниться в РФ. Владелец выбирает
домен, сервер и сервисы; юридические тексты и реквизиты проверяет юрист.
В seed остаются заготовки, поэтому сама успешная сборка не разрешает запуск
платежей или публикацию медицинских уроков.

На сервере оператор:

1. Устанавливает Docker Engine с Compose, настраивает SSH, firewall и DNS
   домена на сервер. Входящие 80/443 должны быть доступны Caddy; SSH ограничен.
2. Кладёт проект в `/opt/emil2`, копирует шаблон:

   ```bash
   cp infra/production/env.example .env.production
   chmod 600 .env.production
   ```

3. Заполняет `.env.production`: домен/APP_URL, случайный пароль базы,
   URL базы с URL-кодированным паролем, почту, LLM, ЮKassa, закрытые S3-бакеты,
   реквизиты и поддержку. Ключи не передаются в переписке и не коммитятся.
   `APP_URL` — HTTPS. Нельзя оставлять пароли `REPLACE_...`.
   `YOOKASSA_TEST_MODE=true` сохраняется до отдельной приёмки оплаты.
4. Для S3 включает версионирование бакета приложения и применяет политику
   `infra/production/app-bucket-lifecycle.json`: активные изображения не
   удаляются; прежние версии хранятся 14 дней. Для отдельного закрытого
   backup-бакета — `backup-lifecycle.json` с хранением 14 дней. Бакеты должны
   быть на одном провайдере/регионе для серверного копирования версий.
   Backup-ключу нужны чтение версий исходного бакета и запись в backup-бакет.
5. Собирает и помечает образы неизменяемым номером версии:

   ```bash
   docker compose --env-file .env.production -f docker-compose.production.yml build web migrate
   ```

   Для обновлений сохраните текущие image ID/tag до сборки. Лучше использовать
   `APP_IMAGE` и `MIGRATE_IMAGE` с точным тегом релиза, а не общий `latest`.

6. После согласованного решения о запуске применяет базу и запускает сервисы:

   ```bash
   docker compose --env-file .env.production -f docker-compose.production.yml up -d postgres
   docker compose --env-file .env.production -f docker-compose.production.yml run --rm migrate
   docker compose --env-file .env.production -f docker-compose.production.yml up -d web worker caddy
   ```

   Эти команды публикуют сайт. В облачной проверке проекта они **не выполнялись**.
   Production-образ требует реальных адаптеров, HTTPS, реквизитов и доверенного
   прокси. Caddy выдаёт сертификат автоматически после настройки DNS.

7. Проверяет `https://ДОМЕН/api/health`, страницы и изолированный тестовый путь
   ученика. Индексация включается `SITE_INDEXING=true` только на согласованном
   публичном домене. До этого robots закрывает весь сайт, sitemap пуст.

`api/health` в production проверяет базу и heartbeat worker не старше трёх
минут. Первому старту worker может понадобиться некоторое время. Веб-контейнеры
работают без root, с read-only файловой системой и временным кешем; SMTP,
платежи, LLM и S3 получают ключи только при запуске. Build не обращается к базе.

## Обновление и откат

1. Сделайте успешную копию и убедитесь, что она есть в отдельном бакете.
2. Зафиксируйте commit и прежние `APP_IMAGE`/`MIGRATE_IMAGE`, сохраните
   конфигурацию в защищённом месте. Соберите новые образы до остановки сайта.
3. Примените миграции отдельной задачей `run --rm migrate`, затем пересоздайте
   web/worker. На время обновления пользователь может получить повтор запроса;
   очередь и финансовые операции идемпотентны.
4. Проверьте health и вход → урок → ответ → повторение. Проверьте worker,
   импорт, логи ошибок и кабинет оплаты. Не считайте один health полной приёмкой.
5. При ошибке совместимого приложения верните прежние теги образов и
   пересоздайте web/worker. Новые добавочные таблицы сохраняются. **Не запускайте
   автоматический откат миграций или восстановление поверх текущей базы.**
   Несовместимые миграции требуют отдельного плана до выпуска.

Если нужен откат данных, сначала восстановите копию в новую базу и новый
бакет/том, проверьте их и переключите конфигурацию. Заказы и списания после
времени копии сверьте с провайдером до запуска worker: восстановление старого
состояния не отменяет реальные деньги и внешние операции.

## Ежедневные копии рабочего сервера

```bash
EMIL2_BACKUP_DIR=/var/backups/emil2 bash scripts/ops/backup.sh production
```

Сначала снимается `pg_dump`, затем копируются версиями неизменяемые S3-файлы,
включая удалённые после снимка базы. Исходный бакет должен иметь версионирование
и хранить прежние версии. Перезапись одного opaque-ключа считается ошибкой.
Архивы, список файлов и SHA-256 отправляются в отдельный закрытый бакет.
`COMPLETE.json` записывается последним: только такой префикс является готовой
удалённой копией. При ошибке передачи команда возвращает ошибку; локальная
копия остаётся. Неполные префиксы убирает политика хранения.

Для расписания проверьте пути в `infra/production/emil2-backup.service`,
установите service/timer в `/etc/systemd/system`, выполните
`systemctl daemon-reload` и `systemctl enable --now emil2-backup.timer`.
Расписание — ежедневно около 03:15 UTC. `EMIL2_PRUNE_EXPIRED=true` в service
удаляет локальные копии старше 14 дней **только при наличии подтверждения
завершённой удалённой передачи**; скрипт не трогает другие папки и симлинки.
Проверяйте `journalctl -u emil2-backup.service` и наличие свежего COMPLETE в
бакете. Ошибка backup-service должна попадать в алерт системы эксплуатации.

В `.env` нет резервной копии секретов: восстановление конфигурации из менеджера
секретов — отдельная часть аварийной процедуры.

## Аварийное восстановление рабочего сервера

1. На чистом сервере с PostgreSQL 16 + pgvector скачайте весь завершённый
   префикс копии из закрытого бакета. `COMPLETE.json` сохраните также под именем
   `OFFSITE_COMPLETE.json`. Не используйте неполный префикс без COMPLETE.
2. Поднимите только postgres и выполните `restore.sh production ПАПКА
emil2_restore_ДАТА`. Утилита проверяет файлы и создаёт отдельную базу.
3. Создайте **новый пустой** закрытый S3-бакет на том же провайдере. Задайте
   `RESTORE_S3_BUCKET`, `RESTORE_S3_ACCESS_KEY`, `RESTORE_S3_SECRET_KEY` в
   защищённой `.env.production`. Restore-ключу нужны чтение backup-бакета и
   запись в новый бакет. Оригинальный бакет приложений не используется как цель.
4. Через образ приложения выполните `node --import tsx scripts/ops/offsite.ts
restore-files /backup`, примонтировав папку копии как `/backup:ro`.
   Утилита проверит контрольную сумму списка файлов и пустоту нового бакета,
   затем скопирует изображения под прежними opaque-ключами. Исходный и
   backup-бакет защищены от выбора в качестве цели. После частичной ошибки
   используйте новый пустой бакет; утилита не затирает существующие файлы.
5. Укажите новую базу и новый бакет в конфигурации web/worker/migrate,
   примените недостающие миграции, проверьте сверку данных и внешних платежей,
   затем включайте сервисы. Старые ресурсы сохраните до окончания проверки.

Локальная проверка в облаке восстанавливала данные и реальные байты изображения
на чистом PostgreSQL в отдельном контейнере. Реальное S3-восстановление требует
приёмки на выбранном провайдере; заглушка SDK проверяет механику, не соединение.

## Мониторинг и диагностика

- Укажите Sentry/GlitchTip DSN в `SENTRY_DSN`. Используется нативный envelope
  transport без SDK, профилирования и Session Replay. Передаются только
  технический код и хеш места ошибки; сообщения исключений, стек, запросы,
  IP, имя, почта, идентификаторы и материалы не отправляются.
- Для правил алертов используйте коды `webhook_failed`, `billing_sync_failed`,
  `billing_tick_failed`, `queue_failed`, `worker_failed`, `llm_budget_exceeded`.
  Ограничение отправки — до 10 событий в минуту на процесс, повтор одного
  fingerprint подавляется на минуту. Настройка адресатов алертов — у владельца
  Sentry/GlitchTip; приложение не рассылает сообщения сотрудникам автоматически.
- Внешний uptime-монитор проверяет `/api/health` раз в минуту. После трёх минут
  без heartbeat worker endpoint станет 503. Не включайте логирование полного
  URL входа: одноразовые ссылки содержат токены. Caddy access log выключен, контекст HTTP-запроса удаляется и из error log.
- В «Логах тьютора» администратор видит оценку расходов всех ИИ-функций.
  Стоимость миллиона входящих/исходящих/поисковых токенов задаётся в
  «Настройках». Ledger анонимный, стоимость фиксируется на момент запроса.
  Неизвестные тарифы или отсутствующий usage не считаются бесплатным запросом.
  Бюджет `LLM_DAILY_BUDGET_RUB` проверяется каждые 15 минут по UTC; алерт
  не останавливает запросы. Счёт провайдера остаётся источником фактических затрат.
- Просмотр журналов:

  ```bash
  docker compose --env-file .env.production -f docker-compose.production.yml ps
  docker compose --env-file .env.production -f docker-compose.production.yml logs --tail=100 web worker
  ```

## Смена ключей

Выпустите новый ключ у провайдера, внесите его в защищённую `.env.production`,
пересоздайте web/worker и проверьте отдельный тестовый запрос. Только после
проверки отзовите прежний ключ. Для ЮKassa и SMTP согласуйте переключение
с провайдером. Смена токена Telegram требует проверки домена виджета.
Если ключ утёк, сначала отзовите его у провайдера, затем обновляйте приложение.

Пароль PostgreSQL меняется и в самом PostgreSQL, и в `.env.production`:
редактирование `POSTGRES_PASSWORD` не меняет пароль существующего тома.
Не удаляйте базу ради смены пароля. Операцию выполняет оператор с отдельным
контролем входа и работающей резервной копией. Изменение SESSION-токенов,
реквизитов, юридических версий и боевых платежей не входит в ротацию ключа.

## Нагрузочная проверка

Сценарий `scripts/load/smoke.js` запускается k6 1.0.0 против отдельной копии
приложения и синтетического бесплатного урока. Он поднимается до 300 VU,
читает лендинг и урок, проверяет health, делает паузу чтения 5 секунд.
Порог: ошибки <1%, p95 страниц <2,5 с, p95 health API <300 мс. Это нагрузка
чтения, не тест внешнего ИИ, платежей, канала 4G или браузерного LCP.
`LESSON_PATH` обязателен, `BASE_URL`, `THINK_SECONDS`, `HOLD` настраиваются.
Запускайте на staging с работающим worker и предварительным прогревом.
Не проводите такой тест на чужом или рабочем сайте без отдельного согласования.

Перед публичным запуском также нужны реальная проверка HTTPS, согласий,
SMTP/Telegram, качества ИИ с преподавателем и оплаты/возврата согласованного
тестового тарифа. Боевой платёж 1 ₽ требует отдельного решения владельца.
