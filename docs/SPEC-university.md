### 1.3 Правила для этапов этого документа

1. Этапы последовательные: 11 → 12 → 13 → 14 → 15 → 16. Следующий этап начинается после мержа предыдущего. Исключение: этап 15 (видео) можно делать параллельно с этапом 14, если этап 13 уже смержен.
2. **Существующие данные неприкосновенны.** Каждая миграция:
   - аддитивная или с переносом данных в той же миграции;
   - проверяется на базе с данными (preview-seed + демо-контент), а не только на пустой;
   - без потери прогресса, карточек, ответов и платежей.

   В PR описать, что миграция делает с существующими строками.

3. Новые зависимости запрещены, если не указаны в этапе. Исключение — обоснование в PR, принимается приёмщиком.
4. Существующие тесты нельзя удалять или ослаблять, чтобы «позеленело». Если тест устарел по смыслу этапа — переписать, объяснив в PR, что он теперь проверяет.
5. Неоднозначность → самый простой вариант + запись в `docs/decisions.md`. Останавливаться и спрашивать только о необратимом: удаление данных, юридические тексты, схема оплаты.
6. Юридические тексты (уведомление студенту в этапе 14) Codex пишет как черновик с пометкой `НУЖНО СОГЛАСОВАНИЕ` и не выдаёт за финальные.

### 1.5 Локальный запуск у владельца (zip + Docker Desktop)

Владелец проверяет каждую версию на своём Mac через Docker Desktop, без Git и без Node.js. Поэтому **после каждого пуша** в ветку PR (первого и каждой доработки) Codex в конце ответа и в разделе «Локальный запуск (zip)» описания PR даёт:

1. **Ссылку на архив актуальной ветки:**
   `https://github.com/emmustfan/emil2/archive/refs/heads/<ветка>.zip`.
   Репозиторий закрытый: ссылка открывается в браузере, где выполнен вход в GitHub. Архив скачивается в «Загрузки» под именем `emil2-<ветка, где / заменён на ->.zip`; внутри одна папка с тем же именем.
2. **Короткий хэш коммита**, который в этом архиве, чтобы владелец мог сверить версию.
3. **Команды для Terminal** — готовые к копированию, с подставленными именами, без заполнителей. Каждая команда — отдельным блоком `bash`, в таком порядке:
   - остановить предыдущую запущенную версию. Каждая папка — отдельный проект Docker с теми же портами 3000/5432/8025: без остановки новая версия не запустится. Данные старой версии при этом сохраняются:
     ```bash
     cd ~/Downloads/<папка предыдущей версии> && docker compose -f docker-compose.yml -f docker-compose.preview.yml down
     ```
     Если владелец не помнит, какая версия запущена, — альтернатива: останавливает все запущенные версии платформы (проекты Docker с именем на `emil2`) и не трогает другие проекты на Mac:
     ```bash
     docker compose ls -q | grep '^emil2' | xargs -I{} docker compose -p {} down
     ```
   - распаковать архив (с перезаписью, если такая папка уже была):
     ```bash
     cd ~/Downloads && unzip -oq emil2-<ветка-через-дефис>.zip
     ```
   - запустить:
     ```bash
     cd ~/Downloads/emil2-<ветка-через-дефис> && bash start-mac.command
     ```
   - остановить после проверки:
     ```bash
     cd ~/Downloads/emil2-<ветка-через-дефис> && docker compose -f docker-compose.yml -f docker-compose.preview.yml down
     ```
4. **Что открыть и проверить руками** — адреса (`http://localhost:3000/...`, письма для входа — `http://localhost:8025`) и тестовые аккаунты для сценариев этого этапа (`owner@example.ru`, `teacher@example.ru`, `student@example.ru` или новые, если этап их добавляет).
5. **Что делать, если не запустилось**: команда просмотра журнала
   ```bash
   cd ~/Downloads/emil2-<ветка-через-дефис> && docker compose -f docker-compose.yml -f docker-compose.preview.yml logs --tail 100 web migrate
   ```
   и просьба прислать вывод.

Правила:

- Новая папка — новая чистая база с демо-данными (данные предыдущей версии остаются в её папке и не переносятся). Если этапу нужно проверить миграцию **существующих** данных, Codex отдельно пишет, как это сделать: запустить сначала версию из `main`, создать данные по шагам, остановить, затем распаковать новую версию **поверх той же папки** (`unzip -oq` в папку с тем же именем) и запустить снова.
- `docker compose ... down -v`, удаление томов и другие команды, стирающие данные, Codex владельцу не даёт.
- Если этап меняет `start-mac.command`, `docker-compose*.yml` или `.env.example`, Codex сам проверяет запуск с нуля в чистой папке и пишет об изменениях в разделе «Локальный запуск (zip)».
- `docs/macos.md` обновляется, если меняется порядок запуска или адреса.

## 3. Целевая модель (обзор)

```
Факультет ─┬─ Кафедра ─── Предмет ─── Раздел ─── Тема (урок)
           │                                       ├─ блоки текста, пропуски, изображения
           │                                       ├─ видеолекции (Rutube) + вопросы в видео
           │                                       └─ тест
           └─ Учебная группа ─┬─ студенты (зачисление)
                              ├─ предметы группы  ──► доступ студентов к предмету
                              └─ преподаватели группы по предмету ──► просмотр прогресса
```

Ключевые принципы:

1. **Владелец контента — кафедра.** Предмет принадлежит ровно одной кафедре. Править его материалы могут только сотрудники этой кафедры (и администратор платформы). Кафедры не видят черновики друг друга и не могут сломать чужие материалы.
2. **Права проверяются в одном месте** — модуль `lib/org`. Ни один сервис не решает сам, может ли пользователь что-то сделать.
3. **Студент видит только опубликованную версию.** Правки идут в черновик, публикация — атомарное переключение.
4. **Авторские права и преподавание — разные вещи.** Автор правит материалы кафедры. Преподаватель группы видит прогресс своих студентов по своему предмету. Один человек может быть и тем и другим.
5. **Данные студента видит только тот, кому это положено по группе.** Каждый просмотр карточки студента журналируется.

## 4. Этап 11. Исправления конкурентности и стабильные пропуски

**Затрагивает:** `lib/lessons/service.ts`, `lib/srs/service.ts`, `lib/tutor/scope.ts`, `lib/tutor/indexing.ts`, `lib/demo/*`, `lib/content/service.ts`, `lib/content/images.ts`, `lib/content/parse.ts`, `lib/editor/extensions.ts`, `components/exercises/inline-gap.tsx`, `docs/lesson-authoring.md`, `docs/exercises.md`.

### 11.1 Блокировки (R1, R2)

1. Создать `lib/content/locks.ts` с двумя функциями на **одном** ключе `content:topic:<id>`:
   - `lockTopicForLearning(tx, topicId)` — `pg_advisory_xact_lock_shared`;
   - `lockTopicForChange(tx, topicId)` — `pg_advisory_xact_lock`.
2. Все операции учащегося переводятся на `lockTopicForLearning`: загрузка урока, ответ на пропуск, старт и ответ теста, открытие и оценка карточки, область тьютора, демо и перенос демо-прогресса.
3. На `lockTopicForChange` переводятся все операции, меняющие видимое студенту:
   - публикация темы;
   - удаление темы;
   - снятие с публикации (появится в этапе 12);
   - загрузка изображений темы;
   - индексация тьютора.

   Порядок захвата фиксируется и документируется в шапке `locks.ts`: сначала `topic:<id>` (редакторская), затем `content:topic:<id>`. Иначе возможна взаимоблокировка.

4. Блокировка учащегося `learning:<actor>` остаётся эксклюзивной: она сериализует действия **одного** студента и нужна.
5. Убрать или исправить неверный комментарий в `lib/lessons/service.ts:185`.

**Приёмка 11.1:**

- Интеграционный тест (детерминированный, без таймингов): транзакция A студента 1 держит блокировку чтения темы и не коммитится. В это время ответ студента 2 на пропуск той же темы **успешно завершается**.
- Интеграционный тест: пока транзакция A держит блокировку чтения, публикация темы **ждёт** и завершается только после коммита A. После этого ответ с прежней `version` получает 409 «Тема обновлена».
- Тест на то, что все перечисленные в п. 2 функции используют `lockTopicForLearning`: через мок или проверку вызова, без grep по исходникам.
- В `docs/decisions.md` — схема блокировок.

### 11.2 Стабильные идентификаторы пропусков (R3)

1. У пропуска появляется **явный id в разметке**. Рекомендуемый синтаксис: id в начале содержимого скобок.
   - `[[#k7f3q2 правильный|дистрактор|дистрактор]]`
   - текстовый пропуск: `[[#k7f3q2 =эталон]]`

   Codex может выбрать другой синтаксис, если требования ниже выполняются и выбор записан в `docs/decisions.md`. Требования:
   - токенизатор TipTap (`lessonGap` в `lib/editor/extensions.ts`) и парсер `lib/content/parse.ts` распознают id;
   - визуальный редактор **не показывает** id автору и **сохраняет** его при любом редактировании текста вокруг и при правке вариантов в окне пропуска;
   - id — 6–12 символов `[a-z0-9]`, либо legacy-значение (см. п. 3).

2. `ParsedGap.gapKey` = явный id, если он есть. Иначе — прежний хэш `makeGapKey`.
3. **Миграция без SQL-переноса.** При первом сохранении темы (`updateTopic`) и при импорте сервер проставляет явные id всем пропускам без id:
   - пропуску, у которого уже есть строка `Gap` с текущим хэшем, — id = этот хэш (40 hex). Так существующие `Gap`, `GapAnswer`, `Card` и `gapExercises` продолжают совпадать;
   - новому пропуску — случайный короткий id.

   Обновлённый `contentMd` возвращается редактору. В теме не может быть двух одинаковых id: при копировании пропуска второй экземпляр при сохранении получает новый id.

4. `gapExercises` остаются ключеванными по `gapKey`; при переназначении id (п. 3, дубликат) настройки копируются.
5. Если при публикации у существующего пропуска **изменился набор правильных ответов**, карточки повторения этого пропуска сбрасываются в `NEW` с `dueAt = now`. Первые ответы студентов (`GapAnswer`) не трогаются. Изменение только текста предложения или дистракторов карточки не сбрасывает.

**Приёмка 11.2:**

- Unit-тесты парсера:
  - правка текста предложения с явным id → тот же `gapKey`;
  - перестановка пропусков → ключи сохраняются;
  - дубликат id → второй получает новый;
  - тема без id → после сохранения id равны прежним хэшам.
- Unit-тест round-trip редактора: markdown с id → TipTap → markdown, id сохранены; правка вариантов через окно пропуска сохраняет id.
- Интеграционный тест: студент ответил на пропуск, автор поменял формулировку и опубликовал. В результате:
  - тот же `Gap.id`;
  - `GapAnswer` на месте;
  - карточка не приостановлена;
  - `TopicProgress` не изменился.
- Интеграционный тест: смена правильного ответа сбрасывает карточку; смена дистрактора — нет.
- Повторная публикация без изменений не меняет id пропусков (существующий тест этапа 2 остаётся зелёным).

## 5. Этап 12. Черновик и опубликованная версия урока

**Цель:** правки опубликованного урока не видны студентам до публикации, а урок не исчезает на время правок (R4, R5).

**Затрагивает:** `prisma/schema.prisma`, `lib/content/*`, `lib/lessons/*`, `lib/srs/*`, `lib/tutor/indexing.ts`, `lib/demo/*`, админку уроков (`components/admin/*`, `app/admin/topics/*`), `docs/lesson-authoring.md`.

### 12.1 Модель

Рабочая копия хранится в отдельных `draft*`-полях. «Живые» поля темы остаются опубликованной версией, поэтому студенческий код почти не меняется.

```prisma
enum DraftState {
  CLEAN      // черновик совпадает с опубликованным
  DRAFT      // есть неопубликованные правки
  REVIEW     // правки отправлены на проверку
}

model Topic {
  // существующие поля title, contentMd, gapExercises, readingMinutes, referencesMd,
  // authorName, reviewerName, reviewedAt, needsExpertReview, aiGenerated
  // = ОПУБЛИКОВАННАЯ версия (для никогда не публиковавшейся темы — пустые/последние сохранённые)
  status            ContentStatus  // = видимость для студентов: PUBLISHED — тема видна
  draftState        DraftState     @default(DRAFT)
  draftTitle        String
  draftContentMd    String         @db.Text
  draftGapExercises Json           @default("{}")
  draftReadingMinutes Int?
  draftReferencesMd String?
  draftAuthorName   String?
  draftReviewerName String?
  draftReviewed     Boolean        @default(false)
  draftUpdatedAt    DateTime?
  draftUpdatedById  String?
  revisions         TopicRevision[]
}

// Неизменяемый снимок каждой публикации — история и основа для будущего отката.
model TopicRevision {
  id            String   @id @default(cuid())
  topicId       String
  version       Int
  title         String
  contentMd     String   @db.Text
  gapExercises  Json
  questions     Json     // снимок опубликованных вопросов: id, stem, options, correctOptionIds, acceptedAnswers, explanation
  publishedAt   DateTime @default(now())
  publishedById String?
  topic         Topic    @relation(fields: [topicId], references: [id], onDelete: Restrict)
  @@unique([topicId, version])
}

model Question {
  // существующие поля = опубликованная версия
  publishedAt  DateTime?  // null — вопрос создан в черновике и студентам не виден
  draft        Json?      // ожидающие публикации изменения полей (та же схема, что questionFields)
  draftDeleted Boolean    @default(false)
}
```

`ContentStatus.REVIEW` для `Topic.status` больше не используется: статус проверки теперь в `draftState`. Значение enum не удалять — оно используется у `Subject` и `Calculator`.

### 12.2 Поведение

1. **Сохранение темы** пишет только в `draft*`. Ставит `draftState = DRAFT`, `draftUpdatedById`, `draftUpdatedAt`. `status` не меняется.
2. **Вопросы:**
   - создание вопроса в опубликованной теме → строка с `publishedAt = null`;
   - правка опубликованного вопроса → `draft`;
   - удаление → `draftDeleted = true`;
   - в никогда не публиковавшейся теме вопросы правятся напрямую, как сейчас.
3. **Отправка на проверку** → `draftState = REVIEW`.
4. **Публикация** — одна транзакция под `lockTopicForChange`:
   - валидация черновика (все текущие проверки `publishTopic`, но по `draft*`-полям);
   - перенос `draft*` в живые поля;
   - применение `draft` и `draftDeleted` вопросов: удалённые → `archivedAt`, их карточки приостанавливаются; новым вопросам ставится `publishedAt`;
   - согласование `Gap`, как сейчас;
   - `version + 1`, `status = PUBLISHED`, `draftState = CLEAN`;
   - создание `TopicRevision`;
   - постановка в очередь индексации тьютора.
5. **Отменить изменения** — копирует опубликованные поля обратно в `draft*`, очищает `draft`/`draftDeleted` у вопросов, удаляет неопубликованные вопросы (`publishedAt = null`). Только для темы, которая уже публиковалась.
6. **Снять с публикации** — `status = DRAFT`, черновик не трогается, отдельная кнопка с подтверждением. До этапа 13 доступна администратору и назначенному учителю. После этапа 13 — по матрице прав.
7. **Структурные поля** (`slug`, `order`, `sectionId`, `isFree`) не версионируются и применяются сразу. `slug` опубликованной темы менять нельзя (422 с объяснением): ломаются ссылки студентов.
8. Все чтения студента (урок, каталог, карта курса, повторение, тьютор, демо, sitemap/SEO) работают только с живыми полями. Вопросы — только с условием `publishedAt != null && archivedAt == null`. Индексация тьютора берёт только опубликованный текст.
9. Предпросмотр «как увидит ученик» (`app/admin/topics/[id]/student-preview`) показывает **черновик**.

### 12.3 Интерфейс автора

- Плашка «Есть неопубликованные изменения» и время последней правки с автором.
- Кнопки «Отправить на проверку», «Опубликовать», «Отменить изменения», «Снять с публикации».
- «Сравнить с опубликованной»: построчный diff markdown и список изменённых, новых и удалённых вопросов. Без новых зависимостей: простой LCS-diff по строкам в `lib/content/diff.ts` с unit-тестами.
- «История публикаций»: список `TopicRevision` (версия, дата, кто опубликовал), просмотр снимка только для чтения.

### 12.4 Миграция

- Для каждой темы `draft*` = текущие живые значения.
- `draftState`:
  - `CLEAN` для `PUBLISHED`;
  - `REVIEW` для `REVIEW`;
  - `DRAFT` для остальных.

  Затем `REVIEW` в `Topic.status` переводится в `DRAFT`.

- `Question.publishedAt`:
  - = `Topic.publishedAt` для вопросов опубликованных тем;
  - для тем с `version > 0`, которые сейчас в `DRAFT` (были опубликованы, потом правились), — тоже `Topic.publishedAt`; такие темы остаются скрытыми, как сейчас;
  - иначе `null`.
- Для каждой темы с `version > 0` создаётся `TopicRevision` текущей версии со снимком текущих значений (`publishedById = null`).

**Приёмка этапа 12:**

- Интеграционные тесты:
  - автор правит текст опубликованной темы → студент получает старый текст; карточки темы выдаются и оцениваются; тьютор отвечает по старому тексту. После публикации студент видит новый текст, `version + 1`;
  - новый вопрос не попадает в тест до публикации; правка вопроса не видна до публикации; удалённый вопрос исчезает только после публикации;
  - «Отменить изменения» возвращает черновик к опубликованному, неопубликованные вопросы удалены;
  - «Снять с публикации» скрывает тему (404 у студента), карточки темы недоступны. Повторная публикация возвращает их;
  - смена `slug` опубликованной темы → 422;
  - каждая публикация создаёт `TopicRevision` с правильным `version` и снимком вопросов.
- Unit-тесты `lib/content/diff.ts`.
- Миграция прогнана на preview-базе с демо-контентом и ответами студентов: число `GapAnswer`, `Card`, `QuestionAttempt` до и после совпадает. Скрипт проверки приложить или описать в PR.
- E2E: автор правит опубликованный урок, второй браузер (студент) видит старую версию, автор публикует, студент после перезагрузки видит новую.
- Обновлён `docs/lesson-authoring.md`: как теперь работают правки и публикация.

### 13.1 Модель

В SQL-миграции — `CHECK`, что заполнена ровно одна область и она соответствует роли:

- `FACULTY_ADMIN` — только `facultyId`;
- `DEPARTMENT_HEAD` — только `departmentId`;
- `AUTHOR` и `REVIEWER` — ровно одно из `departmentId` / `subjectId`.

`User.role` сохраняется как грубый признак рабочего кабинета:

- `ADMIN` — администратор платформы, все права;
- `EDITOR` — сотрудник: есть хотя бы одно назначение `RoleAssignment` или `GroupTeacher` (этап 14);
- `USER` — студент.

`EDITOR` выставляется автоматически при первом назначении и снимается при удалении последнего (кроме `ADMIN`). Каждое изменение увеличивает `roleRevision` и пишет `SecurityAudit`.

### 13.2 Модуль прав `lib/org`


- Роли пользователей не меняются.

**Приёмка этапа 13:**

- Unit-тесты матрицы: каждая роль × каждое действие × «в области» / «вне области» / «соседняя кафедра того же факультета».

- E2E: глава кафедры назначает автора, автор создаёт и публикует тему в своём предмете и не видит предметы другой кафедры.

**Затрагивает:** `prisma/schema.prisma`, `lib/org/*`, `lib/access/*`, `app/cabinet/*`, `app/teacher/*`, новые страницы групп, `docs/groups.md`.

### 14.2 Права (дополнение к матрице 13.3)

| Действие                                                | ADMIN | FACULTY_ADMIN                 | DEPARTMENT_HEAD                      | Преподаватель группы (GroupTeacher) |
| ------------------------------------------------------- | ----- | ----------------------------- | ------------------------------------ | ----------------------------------- |

Преподавателем группы может быть только пользователь с назначением в кафедре предмета (любая `StaffRole` в области этой кафедры или предмета) или `ADMIN`. При назначении `GroupTeacher` пользователь получает `User.role = EDITOR`, если был `USER`.

### 14.3 Сценарии

1. **Создание групп.** FACULTY_ADMIN создаёт группу вручную или загружает CSV (`name;course;academicYear`, UTF-8, разделитель `;` или `,`). Отчёт о результате: создано, пропущено как дубликат, ошибки по строкам.
2. **Код вступления.**
   - 8 символов из алфавита без похожих символов (`23456789ABCDEFGHJKMNPQRSTUVWXYZ`);
   - срок действия по умолчанию 30 дней (`AppSetting group.joinCodeDays`);
   - кнопка «Сменить код» делает старый недействительным;
   - ссылка `/join/<код>` и QR-код для проектора (QR — SVG без новых зависимостей, либо обосновать зависимость в PR).
3. **Вступление студента.**
   - Студент открывает ссылку или вводит код в `/cabinet/groups`; гость сначала входит.
   - Заполняет ФИО: фамилия и имя обязательны, отчество и номер зачётки — нет.
   - Принимает уведомление «Преподаватели группы видят ваш прогресс, ответы на задания, результаты тестов и просмотр видео по предметам группы. Переписка с ИИ-тьютором преподавателям не показывается». Текст хранится в `LegalDocument` с `kind = "group-notice"` и версией. Финальный текст согласует владелец; до этого он помечен `НУЖНО СОГЛАСОВАНИЕ`.
   - Статус — `PENDING` (или сразу `ACTIVE`, если `requireApproval = false`).
4. **Одобрение.** Преподаватель группы видит заявки: ФИО, email или Telegram, дата. Одобряет или отклоняет по одной или все сразу.
5. **Исключение** → `REMOVED`. Доступ по зачислению прекращается на следующем запросе. История ответов сохраняется.
6. Студент может состоять в нескольких группах.
7. Перебор кодов: не больше 10 попыток в минуту на пользователя и на IP через `consumeLimit`.

### 14.4 Доступ

`allowsAccess` в `lib/access/policy.ts` получает третий источник прав: `enrollments: { subjectId }[]`. Это предметы групп, где пользователь `ACTIVE`, а группа не архивирована. `hasAccess` загружает их одним запросом. Подписки и ручная выдача работают как раньше. `hasAccess` остаётся единственной точкой проверки доступа.

### 14.5 Интерфейс студента

- `/cabinet`: блок «Мои группы»; предметы групп — первыми, с пометкой «по зачислению».
- `/cabinet/groups`: вступить по коду; статус заявок; выйти из группы.
- Ссылка «Что видит преподаватель» ведёт на текст уведомления.

**Приёмка этапа 14:**

- Unit-тесты `allowsAccess` с зачислениями:
  - `ACTIVE` даёт доступ;
  - `PENDING`, `REMOVED` и архивная группа — не дают;
  - чужой предмет — не даёт;
  - подписка и зачисление вместе не конфликтуют.
- Интеграционные тесты:
  - вступление по коду → `PENDING` → платная тема закрыта → одобрение → открыта без подписки → исключение → закрыта;
  - смена кода: старый код → «Код недействителен»; просроченный код — так же;
  - перебор кодов упирается в лимит (429);
  - преподаватель группы A не может одобрять заявки группы B (404);
  - DEPARTMENT_HEAD не может открыть группе предмет чужой кафедры.
- CSV-импорт групп: unit-тест разбора (BOM, `;` и `,`, дубликаты, пустые строки, ошибка в строке N).
- E2E: администратор факультета создаёт группу, глава кафедры открывает предмет и назначает преподавателя, студент вступает по ссылке, преподаватель одобряет, студент проходит платный урок.
- Новый `docs/groups.md`.

## 8. Этап 15. Видеолекции (Rutube) и задания к ним

**Цель:** в урок можно вставить видео с Rutube по закрытой ссылке, отслеживать просмотр, задавать вопросы прямо в видео и быстро получать черновик заданий с помощью ИИ.

**Затрагивает:** `prisma/schema.prisma`, новый модуль `lib/video/*`, `lib/content/parse.ts`, `lib/editor/extensions.ts`, `components/lessons/*`, `components/admin/*`, `lib/lessons/*`, `lib/imports/*`, `next.config.ts` (CSP), `docs/video.md`.

### 15.1 Ограничение, о котором пишем честно

Rutube с доступом «по ссылке» не защищает видео: любой, у кого есть ссылка, может его смотреть. Платформа только не показывает ссылку тем, у кого нет доступа к теме. Для MVP это принято.

В интерфейсе автора постоянная подсказка: «Видео доступно всем, у кого есть ссылка. Не размещайте видео, на которых можно узнать пациента без его письменного согласия».

При добавлении видео автор ставит обязательную отметку «В видео нет персональных данных пациентов, либо есть их согласие» — по аналогии с `rightsConfirmedAt` в импорте.

### 15.3 Добавление видео

1. В редакторе урока — блок «Видео». Автор вставляет ссылку или код iframe с Rutube. Поддерживаемые форматы:
   - `https://rutube.ru/video/<id>/`
   - `https://rutube.ru/video/private/<id>/?p=<key>`
   - `https://rutube.ru/play/embed/<id>` и `https://rutube.ru/play/embed/<id>/?p=<key>`
   - `<iframe src="https://rutube.ru/play/embed/...">`
2. Разбор — `lib/video/rutube.ts`, строго:
   - хост `rutube.ru`;
   - `id` — `^[a-f0-9]{32}$`;
   - `p` — `^[A-Za-z0-9_-]{1,128}$`.

   Иначе 422 с подсказкой «Вставьте ссылку вида https://rutube.ru/video/private/…».

3. В `contentMd` записывается **только id `VideoLecture`**, без внешнего id и ключа. Рекомендуемый синтаксис — отдельная строка `::video{#<uuid>}`; другой допустим с записью в `decisions.md`. Требования:
   - парсер выдаёт блок `kind = "video"` с `blockKey`;
   - TipTap сохраняет блок при round-trip;
   - публикация проверяет, что все упомянутые видео существуют, принадлежат этой теме и не архивированы (по аналогии с изображениями).
4. Длительность: автор вводит вручную (`мм:сс` или `чч:мм:сс`). Опционально worker пробует получить её из публичного API Rutube. Ошибка не блокирует сохранение, в тестах — мок, реальный Rutube в тестах не вызывается.
5. Изменение ссылки у существующего видео действует сразу, без публикации. Это осознанное упрощение — записать в `decisions.md`. Новое видео становится видно студентам только после публикации текста, где оно упомянуто.

### 15.4 Безопасность ключа

- `accessKey` и `externalId` **не попадают** в:
  - `contentMd`;
  - ответы API и HTML для пользователей без доступа к теме;
  - события `Event` и Метрику;
  - логи pino;
  - индекс тьютора и запросы к LLM;
  - sitemap и SEO;
  - снимки `TopicRevision`.
- URL плеера `https://rutube.ru/play/embed/<id>/?p=<key>` собирается на сервере только в данных урока для пользователя с доступом.
- Для закрытой темы данные урока не содержат ни одного видеоблока.
- CSP в `next.config.ts`: добавить `https://rutube.ru` в `frame-src`. Фактический список доменов плеера проверить на живом плеере и записать в `docs/video.md`.
- `iframe`:
  - `allow="clipboard-write; autoplay; fullscreen; picture-in-picture"`;
  - `referrerpolicy="strict-origin-when-cross-origin"`;
  - `loading="lazy"`;
  - `title` = название лекции.

  `sandbox` не ставить без проверки, что плеер с ним работает.

### 15.5 Учёт просмотра

1. `components/lessons/rutube-player.tsx` слушает `message` только с `origin === "https://rutube.ru"` и посылает команды плееру через `postMessage` (`{ type: "player:<команда>", data }`). Имена событий и команд проверить на живом плеере и зафиксировать в `docs/video.md` с датой проверки: готовность, смена состояния, текущее время, `player:setCurrentTime`, `player:pause`, `player:play`. Протокол спрятать за адаптером `lib/video/rutube-protocol.ts`, чтобы при изменении API Rutube правка была в одном месте.
2. Во время воспроизведения клиент раз в 15 секунд и при паузе или уходе со страницы (`visibilitychange`, `pagehide`) отправляет просмотренные интервалы:
   - `POST /api/videos/[id]/progress`;
   - тело `{ ranges: [[from, to]], position }`.
3. Сервер (`lib/video/progress.ts`):
   - проверяет доступ к теме;
   - отбрасывает интервалы длиннее 20 с, интервалы за пределами `durationSec + 5` и отрицательные;
   - объединяет интервалы с сохранёнными;
   - считает `watchedSec`;
   - ставит `completedAt`, когда `watchedSec ≥ durationSec × video.completeThreshold` (`AppSetting`, по умолчанию 0.9);
   - лимит 10 запросов в минуту на видео и пользователя.

   Это учёт, а не защита от накрутки, — так и написать в `docs/video.md`.

4. **Запасной вариант.** Если за 10 секунд после `load` iframe от плеера не пришло ни одного события, под плеером появляется кнопка «Я посмотрел лекцию» (`selfReported = true`, `completedAt = now`). Она же доступна, если `durationSec` не задан. Преподаватель видит пометку «отмечено студентом».
5. **Завершение урока.** Если в теме есть видео, урок считается завершённым, когда выполнены прежние условия `completedLesson` **и** все видео темы завершены (по плееру или самоотметкой). Настройка `lesson.requireVideo` (по умолчанию `true`). `TopicProgress` пересчитывается при завершении видео.

### 15.6 Вопросы в видео

1. В форме вопроса — переключатель «Показать в видео» с выбором видео темы и времени (`мм:сс`). `atSec` должен быть в пределах `durationSec`, если тот известен.
2. При воспроизведении, когда позиция впервые пересекает `atSec` неотвеченного вопроса, клиент ставит плеер на паузу и показывает вопрос под плеером. Оверлей поверх кросс-доменного iframe не требуется. После ответа — разбор и кнопка «Продолжить» (play). Можно нажать «Пропустить».
3. Под плеером всегда есть список «Вопросы к видео: N, отвечено M» со ссылками «перейти к моменту» (`setCurrentTime`). Если события плеера недоступны (п. 15.5.4), вопросы показываются этим списком.
4. Ответы:
   - записываются через `TestRun(mode = VIDEO)` и `QuestionAttempt`;
   - правильный ответ и объяснение — только после ответа, как везде;
   - неверный ответ создаёт карточку повторения так же, как ошибка в тесте темы.
5. Вопросы с `videoId` не входят в тест темы, диагностику и демо.

### 15.7 ИИ-черновик заданий к видео

Задача — чтобы на часовую лекцию у автора уходило 10–15 минут проверки, а не часы набора.

1. В карточке видео — кнопка «Сгенерировать задания». Источник:
   - файл субтитров `.vtt` / `.srt` (например, выгруженный из студии Rutube или полученный любым сервисом распознавания речи);
   - расшифровка `.txt` / `.docx`;
   - слайды `.pdf`.

   Используется существующий конвейер `lib/imports` (очередь, лимиты, подтверждение прав, удаление исходника после обработки) с новым форматом `subtitles`.

2. Парсер `.vtt` / `.srt` (`lib/imports/subtitles.ts`, без новых зависимостей) → сегменты `{ fromSec, toSec, text }`. Максимальный объём — в `AppSetting`.
3. LLM получает текст **с метками времени** (без ПДн, как сейчас) и возвращает JSON по zod-схеме:
   - `checkpoints`: 1 вопрос на 5–8 минут лекции; `atSec` — конец фрагмента, к которому вопрос относится; одиночный или множественный выбор;
   - `testQuestions`: 5–10 вопросов к теме;
   - `summaryMd`: конспект с 10–20 пропусками в синтаксисе платформы.

   У каждого задания — `sourceQuote` (дословная цитата) и `sourceSec`.

4. Проверка сгенерированного:
   - `sourceQuote` найдена в расшифровке (нормализованное вхождение), иначе задание отбрасывается;
   - `atSec` в пределах длительности;
   - варианты не повторяются;
   - ровно столько правильных, сколько требует тип.

   Сколько заданий отброшено и почему — в отчёте задачи.

5. Результат попадает в **черновик** темы (этап 12):
   - вопросы с `publishedAt = null`, `aiGenerated`;
   - конспект добавляется в конец `draftContentMd` отдельным разделом «Конспект лекции»;
   - тема — `needsExpertReview`.

   Автор правит или удаляет задания в существующем интерфейсе и публикует обычным порядком. Рядом с каждым ИИ-заданием в редакторе видна цитата-источник и ссылка «перейти к моменту».

6. Расход учитывается в `LlmUsage`. Бюджет `LLM_DAILY_BUDGET_RUB` действует. В тестах — `MockLLMProvider` с фикстурой.
7. Распознавание речи из самого видео — **не в этом этапе** («Позже», раздел 11).

**Приёмка этапа 15:**

- Unit-тесты `lib/video/rutube.ts`: все форматы ссылок и iframe; чужие хосты, неверный id и инъекции в `p` → ошибка.
- Unit-тесты объединения интервалов: повтор того же интервала не увеличивает `watchedSec`; прыжок в конец не даёт завершения; слишком длинный интервал отброшен; граница `completeThreshold`.
- Интеграционный тест утечек. Для пользователя без доступа ответ данных урока и HTML страницы закрытой темы не содержат ни `externalId`, ни `accessKey`. Сериализаторы событий, логов и индекса тьютора их не содержат (проверка на фикстуре с известными значениями).
- Публикация с упоминанием несуществующего, чужого или архивного видео → 422 с номером строки.
- Вопрос в видео не входит в тест темы; ответ на него создаёт `QuestionAttempt` в прогоне `VIDEO`; ошибка создаёт карточку.
- `lesson.requireVideo`: урок без досмотренного видео не завершён; после самоотметки — завершён.
- E2E с **фейковым плеером**: тестовая страница-фикстура, реализующая тот же протокол `postMessage`, подставляется вместо Rutube через настройку окружения только для тестов. Проверяются пауза на вопросе, ответ, продолжение и учёт просмотра.
- Импорт `.vtt`-фикстуры с моком LLM даёт ≥ 5 вопросов в видео с корректным `atSec`, ≥ 5 вопросов теста и конспект с пропусками. Всё в черновике и `needsExpertReview`. Задание с выдуманной цитатой отброшено.
- В PR — ручная проверка на **реальном** закрытом видео Rutube: воспроизведение, события, пауза на вопросе, полноэкранный режим, мобильный Safari и Chrome. Скриншоты.
- Новый `docs/video.md`: форматы ссылок, протокол плеера с датой проверки, ограничения, как генерировать задания.

## 9. Этап 16. Прогресс и ответы студентов для преподавателя

**Цель:** преподаватель видит по каждому студенту своей группы прогресс, все ответы, тесты, просмотр видео и повторение, а также проблемные темы и задания группы (R7).

**Затрагивает:** `prisma/schema.prisma`, `lib/lessons/service.ts`, новый модуль `lib/progress/*`, `lib/org/*`, `app/teacher/groups/*`, `docs/teacher-progress.md`.

### 16.1 Данные

```prisma
// Журнал ВСЕХ попыток ответа на пропуск, включая практику. GapAnswer остаётся «первым ответом» для оценки.
model GapAttempt {
  id           String   @id @default(cuid())
  gapId        String
  userId       String
  topicVersion Int
  chosenValues String[]
  chosenText   String?
  isCorrect    Boolean
  practice     Boolean
  createdAt    DateTime @default(now())
  @@index([userId, createdAt])
  @@index([gapId, createdAt])
}

// Журнал просмотров данных студента сотрудниками.
model StudentDataAccess {
  id        String   @id @default(cuid())
  viewerId  String
  studentId String
  groupId   String?
  subjectId String
  view      String   // "student_card" | "export"
  createdAt DateTime @default(now())
  @@index([studentId, createdAt])
}
```

- `answerGap` пишет `GapAttempt` на **каждый** ответ авторизованного пользователя, включая практику. Демо-сессии не пишутся.
- Миграция переносит каждый `GapAnswer` с `userId` в `GapAttempt` (`practice = false`, `createdAt` из `GapAnswer`, `topicVersion` = текущая версия темы).
- Источники остальных данных — существующие таблицы: `TopicProgress`, `TestRun` / `QuestionAttempt`, `Card` / `ReviewLog`, `VideoProgress`, `TutorMessage` (только количество).

### 16.2 Права

`progress.view` для пары «группа + предмет»:

- `GroupTeacher` этой пары;
- `DEPARTMENT_HEAD` кафедры предмета (все группы с этим предметом);
- `FACULTY_ADMIN` факультета группы;
- `ADMIN`.

Видны **только** данные по этому предмету. Другие предметы студента не раскрываются. Нет права → 404.

### 16.3 Страницы

1. **`/teacher/groups`** — мои группы: группа, курс, учебный год, предмет, число студентов, число заявок, средняя доля завершённых тем.

2. **`/teacher/groups/[groupId]/subjects/[subjectId]` — журнал.**
   - Строки — студенты (`ACTIVE`, по фамилии); переключатель «показать исключённых».
   - Столбцы — темы предмета в порядке курса, сгруппированные по разделам.
   - Ячейка — статус (не начата / в процессе / завершена), доля верных первых ответов на пропуски, лучший балл теста, отметка о видео (по плееру / самоотметка / не смотрел). Цвет по шкале; во всплывающей подсказке — подробности.
   - Итог по строке: завершено тем X из N, средний балл тестов, карточки к повторению и просроченные, последняя активность.
   - Итог по столбцу: доля завершивших, средний балл.
   - Фильтры: раздел; «только отстающие» (завершено меньше X% или нет активности больше N дней, оба порога — `AppSetting`).
   - Экспорт CSV: UTF-8 с BOM, `;` — открывается в Excel с кириллицей. Пишет `StudentDataAccess(view = "export")`.

3. **`/teacher/groups/[groupId]/subjects/[subjectId]/students/[userId]` — карточка студента.** Пишет `StudentDataAccess(view = "student_card")`.
   - Шапка: ФИО, группа, номер зачётки, последняя активность, итоги.
   - По каждой теме (раскрывающийся список):
     - пропуски: текст с пропуском, первый ответ, правильный ответ, все попытки с датой и временем и пометкой «практика»;
     - тесты: каждый прогон (дата, балл, длительность) с ответом студента и правильным ответом по каждому вопросу;
     - видео: процент просмотра, способ учёта, ответы на вопросы в видео.
   - Повторение: карточек всего, к повторению, просрочено; распределение оценок за 30 дней с подписью «самооценка студента».
   - Активность: число действий по дням за 30 дней (простая полоса без библиотек графиков).
   - Тьютор: только число вопросов по темам. **Содержимое переписки не показывается.**
   - Если ответ дан к прежней версии темы, а задание с тех пор изменилось, — пометка «ответ к версии N».

4. **`/teacher/groups/[groupId]/subjects/[subjectId]/analysis` — анализ заданий.**
   - По каждому пропуску и вопросу: число ответивших, доля верных первых ответов, три самых частых неверных ответа с количеством.
   - Сортировка от худших.
   - Ссылка «Открыть в редакторе», если у пользователя есть `content.edit` на предмет.

5. **Заявки на вступление** (из этапа 14) — вкладка в странице группы.

### 16.4 Производительность

- Журнал строится фиксированным числом агрегирующих запросов, без N+1. Основа — `TopicProgress`; количество запросов не зависит от числа студентов.
- Скрипт `scripts/preview/teacher-demo.ts` создаёт группу из 40 студентов, предмет на 80 тем и правдоподобную активность.
- Бюджет: серверная отрисовка журнала ≤ 1 с (p95) на этих данных локально; карточка студента ≤ 700 мс. Замер — в PR.

### 16.5 Прозрачность для студента

- В кабинете студента у каждого предмета группы — «Что видит преподаватель» (текст уведомления из этапа 14).
- Студент видит свои собственные попытки по пропускам в уроке («история ответов»).

**Приёмка этапа 16:**

- Интеграционные тесты прав:
  - преподаватель группы A по предмету X видит журнал и карточки только студентов A и только по X;
  - группа B, предмет Y или студент вне группы → 404 и на страницах, и в экспорте;
  - глава кафедры видит все группы со своим предметом;
  - FACULTY_ADMIN — все группы факультета.
- Согласованность: числа в журнале по студенту совпадают с его собственным прогрессом в кабинете (тест на одной фикстуре).
- Все попытки, включая практику, видны с отметками времени. Перенесённые первые ответы на месте.
- Каждый просмотр карточки и каждый экспорт создают `StudentDataAccess`.
- CSV: unit-тест экранирования (`;`, кавычки, переводы строк, формулы `=`, `+`, `-`, `@` в начале ячейки экранируются против CSV-injection).
- Обезличенный (удалённый) студент показан как «Удалённый пользователь» без ФИО и контактов.
- Регрессия: правильные ответы по-прежнему не уходят **студенту** до ответа.
- Замер производительности по 16.4 в PR.
- E2E: преподаватель открывает журнал, видит отстающего, открывает карточку, видит неверный ответ и правильный, выгружает CSV.
- Новый `docs/teacher-progress.md`.

## 10. Решения по умолчанию и вопросы владельцу

Codex не ждёт ответа: использует значение по умолчанию, а владелец может поменять его позже настройкой или отдельной задачей.

| Вопрос                                      | По умолчанию                                                                  |
| ------------------------------------------- | ----------------------------------------------------------------------------- |
| Кто создаёт группы                          | Администратор факультета (или платформы)                                      |
| Нужно ли одобрение вступления               | Да (`requireApproval = true`), выключается у группы                           |
| Текст уведомления «что видит преподаватель» | Черновик Codex с пометкой `НУЖНО СОГЛАСОВАНИЕ`, финальный утверждает владелец |
| Нужен ли досмотр видео для завершения урока | Да (`lesson.requireVideo = true`)                                             |
| Порог досмотра                              | 90%                                                                           |
| Отдельный рецензент перед публикацией       | Нет, включается у кафедры                                                     |
| Видит ли преподаватель переписку с тьютором | Нет, только количество                                                        |
| Платная подписка для студентов вне групп    | Остаётся как есть                                                             |

## 11. Не делаем в этих этапах («Позже», но архитектурно не закрываем)

- Механики в стиле Duolingo / ЕГЭ-Эспрессо: граф навыков, ежедневная сессия, серии дней, XP, лиги, FSRS вместо SM-2.

- Единый вход университета (LDAP/Keycloak/ADFS), импорт групп из 1С:Университет, LTI/Moodle.

- Настройки с наследованием «университет → факультет → кафедра → предмет» (кроме `requireSeparateReviewer`).
- Добавление студентов списком email и приглашения письмом.
- Учёт времени в уроке, экспорт XLSX, мобильное приложение.
- Откат к прошлой версии урока (история `TopicRevision` уже есть — откат будет отдельной задачей).

## 12. Чек-лист приёмки (что проверяет приёмщик в каждом PR)

**Блокеры** — PR не принимается:

1. Не выполнен критерий приёмки этапа, или выполнение ничем не подтверждено.
2. Потеря или искажение существующих данных при миграции; миграция не проверена на базе с данными.
3. Доступ мимо `lib/access` (учебные данные) или мимо `lib/org` (права сотрудников); отсутствуют тесты изоляции.
4. Утечка: правильные ответы студенту до ответа; `accessKey` / `externalId` видео без доступа; данные студента вне области преподавателя; ПДн в LLM, логах или аналитике.
5. Удалённые или ослабленные тесты без объяснения; красный CI.
6. Работа за пределами этапа, которая меняет поведение других модулей.

**Важно** — исправить в этом же PR:

- эксклюзивные блокировки там, где достаточно разделяемых; N+1 в списках;
- тексты интерфейса не на русском или не в общем словаре;
- новая зависимость без обоснования;
- не обновлены `docs/decisions.md` и документы этапа.

**Замечания** — можно отдельной задачей: стиль, именование, мелкие упрощения.

Вердикт приёмщика: «Принято» / «Принято с замечаниями (список)» / «Не принято (блокеры)».
